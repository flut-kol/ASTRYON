# DPP-047: query profiles under tenant distributions (2026-10-21)

Tool: `scripts/bench/query-profiles.sh` (throwaway ClickHouse 24.8, 6 GB container limit, MergeTree with the real
`0001_events_normalized` schema, 10M rows per scenario, 200 tenants, 5 sources, 30 days, payload 200-500 B).
The two SQL shapes are copied from `services/query-api` (`LIMIT 1 BY` dedup before paging/aggregation). Per-query
caps mirror query-api defaults: `max_memory_usage=2e9`, `max_execution_time=30`, `max_threads=4`.
`clickhouse-benchmark`, 60 iterations per cell, 1 and 16 concurrent clients, single node, warm page cache.

Scenarios: **uniform** (every tenant 0.5%), **skewed** (tenant share ~ rand^4: largest 26.6%), **hot** (one tenant 80%).
`events` = 7-day window, first page of 100; `aggregate` = 30-day count by event_type. "hot/largest" = tenant 0.

## Findings
1. **Isolation by tenant size works for small tenants**: tail tenants stay at p95 <= 118 ms at 16 clients in every
   scenario, including next to an 80% tenant (but that was with the big tenant idle; query+ingest+big-tenant mixes are DPP-059).
2. **A large tenant is expensive in both shapes**: 2.7M rows -> aggregate p50 736 ms, 8M rows -> 2.1 s with a single
   client. Follow-up experiment (hot tenant, 8M rows, 1 client, p50, same node):

   | variant | p50 |
   |---|---|
   | aggregate as in query-api (`SELECT *` + `LIMIT 1 BY`) | 2109 ms |
   | same, only the 5 needed columns | 2183 ms (no gain: my first guess about `payload` reads was wrong) |
   | `uniqExact(source_id, event_id, processing_version)` instead of `LIMIT 1 BY` | 1019 ms |
   | `uniq(event_id)` (approximate) | 88 ms |
   | no dedup, plain `count()` | 51 ms |

   So the cost is the exact dedup over millions of keys, not column reads. Events page: 690 ms for the hot tenant;
   a projection ordered by `(tenant_id, event_time, event_id)` brings it to 617 ms (-10%) and roughly doubles
   storage (619 MiB total for 10M rows with it), so it is not worth it.
3. **Concurrency x memory cap is the real limit**: 16 concurrent queries of a hot tenant exceed 2 GB each, so they
   fail or take the node down. The per-tenant concurrency limit in query-api must stay below
   (node memory / `QUERY_MAX_MEMORY_BYTES`), and a hot tenant should have its own lower concurrency.
4. Applied 2026-10-21: `count`-only aggregates in query-api now use `uniqExact(source_id, event_id, processing_version)` (exact, ~2x; mixed metrics keep `LIMIT 1 BY`). Still open: serve them from the
   pre-aggregated 0003 tables (~50 ms class, no per-row dedup, but those are hourly and only for the metrics they hold);
   accept approximate counts only if the API contract says so. Narrower `SELECT` and an events projection: rejected by measurement.

## Limits of this run
Single node, no ingestion running, warm cache, synthetic uniform payloads, 60 iterations per cell (p99 is noisy),
no replicated/distributed table. Numbers are relative, not capacity figures.
