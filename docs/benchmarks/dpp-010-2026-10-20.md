# DPP-010 — ingestion benchmark, 2026-10-20

## Scope and result

This is an **ingestion ACK** benchmark for `gateway -> Kafka raw.events.v1`, not
an end-to-end processing benchmark. The 120k events/s and 250 ms p95 ACK goals
were not met on this single-node development profile. The highest observed
accepted rate was 45,318.1 events/s when the requested rate was 120,000
events/s; p95 ACK was 420.3 ms.

No events failed or were quarantined. The sum of Kafka end offsets after all
runs was 1,199,500, exactly matching accepted events.

## Environment

- Date: 2026-10-20.
- Host: macOS 26.6.1, ARM64, 10 logical CPUs, 16 GiB RAM.
- Kafka: one `apache/kafka:3.9.0` KRaft broker, six partitions for
  `raw.events.v1`, plaintext, RF=1.
- Gateway: local Go build, Kafka publisher, dev static authentication, no TLS.
- Load generator: local Go build; one tenant, 1 KiB approximate serialized
  event, batch size 100, 128 workers, no duplicates or invalid events.
- Every run lasted 10 seconds. The temporary `astryon-bench` Compose project
  was isolated from the ordinary dev stack.

## Results

| Requested events/s | Accepted events/s | Accepted | p50 ACK | p95 ACK | p99 ACK | Failures |
|---:|---:|---:|---:|---:|---:|---:|
| 10,000 | 9,913.2 | 100,000 | 131.9 ms | 360.3 ms | 687.0 ms | 0 |
| 25,000 | 24,531.1 | 247,800 | 264.6 ms | 486.7 ms | 564.4 ms | 0 |
| 50,000 | 37,530.7 | 386,900 | 254.6 ms | 579.0 ms | 980.6 ms | 0 |
| 120,000 | 45,318.1 | 464,800 | 258.7 ms | 420.3 ms | 748.9 ms | 0 |

The exact byte rate from loadgen ranged from 9.251 MB/s at the 10k profile to
42.362 MB/s at the 120k requested profile. HTTP status was 200 for every
request in each valid run.

## Interpretation and next actions

- The gateway/Kafka path accepts all loadgen requests, but misses the 250 ms
  p95 ACK target even at 10k events/s in this environment.
- Throughput stops tracking the requested rate between 25k and 50k; the
  benchmark demonstrates saturation but does not prove which component is the
  bottleneck. Capture Go CPU/heap profiles, Kafka broker metrics, host CPU,
  disk and network telemetry before tuning.
- These numbers cannot justify production capacity or the 120k target: they
  omit TLS/SASL, RF=3/acks=all, an AAS verifier, stream processing, sink,
  ClickHouse, tenant skew, faults and a sustained duration.
- Repeat after producer batching/partition and resource tuning, then include a
  processor and ClickHouse sink to measure end-to-end latency and backlog drain.

## Reproduction profile

Start an isolated Compose project, create topics, build the gateway and
`tests/load` binaries, then run each rate with:

```bash
LOADGEN_TOKEN=<the-local-ASTRYON_DEV_TOKEN> \
LOADGEN_TENANT_ID=0a1b2c3d-1111-4222-8333-444455556666 \
  ./loadgen -url http://127.0.0.1:18082/v1/events/batch \
  -rate <10000|25000|50000|120000> -duration 10s -batch 100 \
  -concurrency 128 -event-size 1024 -dup-ratio 0 -invalid-ratio 0
```

The development static token is deliberately local-only; it is not an AAS
credential and must not be used outside the benchmark environment.
